**Контрольный RET-15 (24.11, PR #93):**
[два ограниченных прохода поиска](https://github.com/dpsmpx/DP_Knowledge_System/pull/93)
сначала приоритизируют полное совпадение терминов, затем дополняют OR-выдачу
с исключением дубликатов. На **20 000 полностью искусственных записей** с
четырьмя заведомо релевантными источниками для каждого из четырёх запросов
`recall@24` вырос с `0/4` до `4/4`, `precision@6` составила `4/6`;
локальная Python/SQLite 3.53.1 SQL-модель показала p50 около `0.20 ms` и
p95 около `0.24 ms`. **318 Python PASS, GitHub CI 8/8 PASS.** Это
намеренно неблагоприятный синтетический пример, не Android-производительность,
не репрезентативное качество семантического поиска и не закрытие всего
RET-15. Ещё требуются более разнообразные размеченные запросы, синонимы,
сравнение моделей и измерения на Android, а также LLM-grounding.

**Контроль LLM-источника (24.11, PR #95):**
[проверка индексного текста SHA-256](https://github.com/dpsmpx/DP_Knowledge_System/pull/95)
теперь сравнивает свежий декодированный Markdown с содержимым именно той
производной FTS4-записи, которая индексирована для текущих пути, времени,
размера и поколения сканирования. Это блокирует отправку изменённого текста
при сохранённом размере и искусственно восстановленном mtime в **обоих**
режимах LLM-поиска. Нет изменения Markdown, журнала, формата базы и
автоматического пересоздания индекса; Android/Python CI **8/8 PASS**.
Проверяются **декодированные UTF-8 тексты**, а не исходные байты файла и
не версия эмбеддингов: raw-byte seal, FTS/embedding согласованность и
семантическая достоверность остаются открытыми.

**Контроль исходных байтов (24.11, PR #97):**
[локальная печать SHA-256 исходного Markdown](https://github.com/dpsmpx/DP_Knowledge_System/pull/97)
перед передачей LLM теперь сверяется с точными байтами, считанными для
выдержки, и с декодированной FTS4-записью в **обоих** режимах поиска.
Производная SQLite-схема v4 хранит хеш и постепенно переносит прежние
записи v1–v3: при первом сканировании повторно читает исходник, проверяет
его текст, сохраняет исходные эмбеддинги для совпавших записей, а
несовпавшие переиндексирует. Пока отсутствует печать, передача LLM
блокируется. Локально **319 Python PASS**, синтетический тест миграции v3
и JVM-регрессия одинакового декодирования разных невалидных UTF-8 байтов
добавлены; аппаратная проверка ещё не проводилась. **Открыты:** независимый
хеш-провананс эмбеддингов, корректировка уже запечатанных строк после
скрытых правок с восстановленным mtime/size (индекс остаётся stale до
изменения метаданных/перестроения), репрезентативные retrieval/grounding,
реальный LLM и физическое QA. Это **не** закрывает RET-15 или LLM-16.

**Привязка эмбеддингов (24.11, PR #99):**
[SQLite v5 и проверка версии источника](https://github.com/dpsmpx/DP_Knowledge_System/pull/99)
добавляют SHA-256 исходного Markdown к каждому чекпоинту эмбеддингов.
Повторное использование, продолжение пакетной индексации, подсчёт и
семантический поиск разрешены только при совпадении хеша с производным
индексом текущего поколения. Перед и после каждого внешнего пакета,
отправляемого **только по согласию пользователя**, приложение перечитывает
файл и проверяет исходные байты. Старые векторы v1–v4 остаются на диске,
но **не считаются актуальными** и не участвуют в поиске до нового ручного
подтверждения обработки. Добавлен синтетический `EMBED-SOURCE-19` без сети;
локально **320 Python PASS**. Это доказательство локальной связки данных,
не криптографическая аттестация удалённой модели. Остаются скрытые изменения
источника с прежним mtime/size до перестроения, широкая проверка качества
векторов, живой провайдер и физическое QA; RET-15 и LLM-16 всё ещё частичны.

**Лексическая точность RET-15 (24.11, PR #101):**
[трёхпроходный FTS4-поиск](https://github.com/dpsmpx/DP_Knowledge_System/pull/101)
теперь отдаёт приоритет короткой последовательной фразе из 2–4 слов,
затем совпадению всех слов и только потом частичным OR-результатам.
Английские/русские вопросительные слова отбрасываются только при наличии
других информативных терминов; пользовательские FTS-операторы не исполняются.
Противоположные искусственные утверждения сохраняются как **отдельные**
источники — никакого выбора «истинного» результата не происходит.
На 20k искусственных строк с большим количеством ранних раздельных совпадений
прошлый двухпроходный алгоритм имел `recall@24=0/4`, а трёхпроходный — `4/4`
для каждого из четырёх размеченных запросов; `precision@6=4/6`, host SQLite
3.53.1 p50 около 0.27 ms, p95 около 0.39 ms. Добавлены Python- и JVM-
регрессии, отдельный синтетический Android `LEX-PHRASE-19`, локально
**323 Python PASS**. Сценарий заведомо сконструирован в пользу фразового
приоритета; это **не** представительская оценка качества поиска, модели,
синонимов или Android. RET-15 остаётся **частичным**, аппаратный QA не выполнен.

**Локальная привязка цитат LLM-16 (24.11, PR #103):**

**Структурное покрытие ссылками LLM-16 (24.11, PR #105):**

похожие на ссылки числа внутри Markdown code fences, inline code,

**Изменение источников во время генерации LLM-16 (24.11, PR #113):**

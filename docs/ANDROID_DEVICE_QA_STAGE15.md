# Stage 15 — встроенная диагностика Android (в том числе без ПК)

Этот документ описывает **реализованные сценарии**, но не утверждает, что они
уже успешно выполнены на физическом Redmi Note 13. Сборка и unit-тесты CI не
подменяют испытания на устройстве.

## Запуск

1. Установить **подписанный** `com.dpsmpx.dpks` из GitHub Releases. Если прямое
   скачивание через браузер даёт некорректный APK, скачать тот же файл в
   Termux и сравнить SHA-256 с опубликованным `.sha256` перед установкой.
2. Открыть **Библиотека знаний**. Желательно дождаться окончания обычного
   обновления индекса, чтобы не смешивать два параллельных замера.
3. Нажать **«Диагностика и копирование»**. Вверху экрана отображаются название
   выполняемого шага и, где возможно, число обработанных синтетических заметок.
4. По завершении появится отчёт, **автоматически скопированный в системный буфер
   обмена**. Кнопка «Скопировать отчёт ещё раз» повторяет копирование.
5. Для замера производительности нажать **«Стресс 20 тыс. и копирование»**.
   Это отдельный продолжительный тест, который создаёт **20 000 синтетических**
   заметок в приватном кэше приложения, строит **отдельную** SQLite FTS-базу,
   проверяет поиск и целостность, затем удаляет свои временные файлы.
6. Во время работы кнопки превращаются в «Остановить проверку». Отмена
   прерывает следующие шаги и пытается удалить все тестовые файлы.

**Никаких подключений к LLM/облаку, принятия решений или исправлений заметок**
этот механизм не выполняет. В частности, проверка настоящего vault считывает
только его список файлов и размеры (для числа заметок и больших файлов),
не выводит имена, пути или содержимое. Реальный производный индекс открывается
для диагностики **только на чтение**. Тестовая база создаётся по отдельному
пути в `getCacheDir()`, а не рядом с реальной базой.

## Что именно проверяется

| Код | Реальная процедура | Что доказывает PASS |
|---|---|---|
| `ENV-01` | `applicationId`, API, ABI, приватный кэш и свободное место | Исполняется ожидаемый пакет; кэш доступен |
| `SCAN-01` | Чтение метаданных выбранного vault, счёт файлов, больших файлов и недоступных директорий | Перебор завершился без исключения; неполнота отдельно помечена WARN |
| `INDEX-01` | SQLite `quick_check`, связи FTS и исходников, векторных таблиц, last scan | Отчёт о реальном индексе успешно получен, `healthy` показывается отдельно; неполнота — WARN |
| `MD-01` | Разбор синтетического Markdown, ссылки и fenced-code | Заголовок и допустимая ссылка извлекаются, ложная ссылка исключается |
| `CORE-01` | Вызов настоящего Python `ksys_android_bridge.inspect_note` с искусственным источником | Ядро работает и сообщает lossless coverage |
| `EMBED-01` | Нормализация/float32 roundtrip/косинус и LSH | Математические примитивы согласованы (не проверяет модель или API) |
| `CRYPTO-01` | AES-GCM зашифрование/расшифровка искусственной строки и проверка подделанного тега | Криптографический формат работает; настоящий журнал не открывался |
| `SANDBOX-01` | Индексация трёх искусственных заметок отдельным FTS, поиск, integrity, повторное индексирование | Реальный код SQLite индексации и поиска выполняется; повторный запуск переиспользует записи |
| `STRESS-20K` | Опционально: генерация 20k, scan, FTS index, search, `quick_check`, hash исходного синтетического файла | Замер в отчёте описывает именно проведённый тест (не потребление батареи в иных условиях) |
| `BG-01` | Чтение настроек WorkManager и разрешения оповещений | Настройки доступны (не доказывает доставку Android JobScheduler) |
| `MANUAL-*` | Отдельные сценарии с LLM, системой, сетью, питанием, разрешениями | **SKIP:** не выполнены этим прогоном |
| `DEBT-01` | Полные app backup/import, cloud sync, ежедневная копия, сложные восстановительные пути | **SKIP:** не реализовано/не проверено, не считать завершённым |

`PASS` означает **только успешность указанной узкой проверки**, не «проект
полностью готов». `FAIL` не содержит исходные сообщения об исключениях:
они могут раскрывать имена файлов. Вместо них пишется только тип ошибки,
например `SQLiteException`, с обозначением этапа и длительностью.

## Ресурсы, отмена, приватность

- Для `STRESS-20K` требуется минимум **128 MiB доступного приватного кэша**;
  иначе нагрузочный шаг получает `SKIP`. Фактическое место требуется под
  небольшие искусственные файлы и SQLite-индекс, проверяется до запуска.
- Подготовка и индексирование 20 000 файлов могут быть длительными на слабом
  накопителе; приложение остаётся интерактивным. Не сворачивать/не убивать
  приложение, если нужен достоверный полный замер. Остановка Activity отменяет
  тест. ОС может прервать приложение самостоятельно — это отдельный сценарий.
- Временные файлы помещаются в индивидуальную папку `dpks-device-qa-*`
  **внутри приватного кэша** и убираются после окончания/ошибки/отмены.
  При внезапном убийстве процесса Android может оставить остаток в кэше;
  его можно удалить стандартной функцией **«Очистить кэш»** Android, не
  выполняя «Очистить данные».
- Отчёт содержит имена тестов, версию, Android API/ABI, количество заметок,
  статистику целостности и время; **не содержит** имена или тексты личных
  заметок, реальные пути, пароли, URL, токены и ответы моделей.
- Буфер обмена Android **не является защищённым хранилищем**: вставляйте лог
  только туда, куда намерены, и при желании очистите буфер после отправки.
- Отправка отчёта владельцу/разработчику осуществляется самим пользователем.
  Приложение не передаёт отчёт автоматически.

## Критерии закрытия Stage 15

1. Быстрый прогон на Redmi Note 13 (Android 15): сохранить отчёт, изучить
   `FAIL`/`WARN`; отдельно зафиксировать корректность отображения и копирования.
2. Стресс 20k: записать `syntheticNotes=20000`, `indexingMillis`, итоговое
   число в SQLite и статус `healthy`; записать время, батарею и используемую
   память отдельно. Перед прогоном лучше иметь достаточно заряда.
3. Повторить проверку без интернета. Убедиться, что синтетический QA и
   офлайн-поиск не требуют API или внешнего сервера.
4. Вручную проверить выполнение/отмену WorkManager-проверок, разрешения
   уведомлений, поведение после сворачивания и системного принудительного
   завершения, а также восстановление индекса **после отдельного разрешения**.
5. Проверить реальную установку подписанного APK (не только `apksigner verify`)
   и соответствие хеша `.sha256`. Записать итог, версию и статус проверки.
6. Не закрывать отдельные продуктовые долги Stage 16+ лишь потому, что прошёл
   QA ранних функций. Все нерешённые долги остаются в общем плане проекта.

Для последующих этапов применять тот же подход: новая проверка получает
**стабильный ID**, синтетические фикстуры, код отчёта и явные `SKIP/MANUAL`
для сценариев, которые приложение не может доказать самостоятельно. Не
автоматизировать принятие фактов или эксфильтрацию пользовательских данных.

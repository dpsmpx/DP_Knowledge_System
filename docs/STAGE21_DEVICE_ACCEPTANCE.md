# Stage 21 — аппаратная приёмка владельцем Android

**Статус: НЕ ПРОЙДЕНА.** Это сценарий ручной проверки, а не акт приёмки.
Владелец 20.11.2026 разрешил подписанный тестовый APK из GitHub Releases;
никакого разрешения объявлять Stage 21 полноценным релизом не было.
Использовать только вымышленные заметки и тестовые пароли.

## Подготовка и существующие кнопки QA

1. Установить подписанный Stage 21 QA APK из GitHub Releases, открыть
   **Процессы → Проверки** и нажать существующую кнопку
   **«Проверить Stage 21 и устройство»**. Ожидать `PORTABLE-21`
   и семь `SYNC21-*`: `CAUSAL-CHAIN`, `METADATA-LOCAL`, `STALE-REFUSAL`,
   `CONTEXT-SOURCE`, `STRUCT-TARGET`, `REJECT-FENCE`, `BATCH-ATOMIC` — `PASS`.
   Отсутствие настоящего двухустройственного/SAF теста должно оставаться
   явным `SKIP`, а не считаться успехом.
2. Запустить существующую кнопку stress для **20 000 синтетических файлов**.
   Зафиксировать время, память, свободное место, отказ при нехватке места,
   перезапуск и повторную индексацию. 20 000 событий журнала — другой тест.
3. Проверить, что QA создавала файлы только в уникальном кэше приложения и
   после завершения удалила свои синтетические данные. Настоящая библиотека,
   журнал, учётные данные и настройки не должны меняться.

## Backup, SAF, секреты, оригиналы

1. Вручную экспортировать зашифрованный DPKSB. Опция секретов должна быть
   **выключена по умолчанию**; при отдельном включении показывается список
   полей и риск, нужен ещё один явный шаг подтверждения. Приватный ключ
   Android Keystore и пароль шифрования никогда не экспортируются.
2. Перенести файл через Android SAF/папку/Syncthing, проверить и восстановить
   в **пустую тестовую библиотеку**. Повторный импорт, неверный пароль,
   повреждённые байты, отмена и недостаток места не должны оставлять
   частично восстановленного состояния.
3. Проверить оба пути оригинального Markdown: незашифрованный `.md` через SAF
   и оригинал из DPKSB. При различиях — хеши, сравнение фрагментов, явное
   **сохранить обе копии**, новое безопасное имя, неизменный локальный файл.
   Дополнительно: Unicode, длинное имя, коллизия, большой текст, отзыв прав,
   закрытие Activity и прерванное копирование.
4. Включить 24-часовую локальную копию только вручную, проверить перезагрузку,
   ограничения батареи/OEM, ротацию копий и отдельно согласованную внешнюю
   папку. Успешный unit-тест WorkManager не доказывает доставку по расписанию.

## Два устройства и запрет отката

1. Сопрячь тестовые устройства, независимо сверив код/QR. Проверить отзыв
   доверия и смену ключа. До сопряжения чужую ветвь нельзя применять.
2. Создать общий синтетический префикс, затем независимо изменить журналы
   офлайн. Передать одну подписанную ветвь через Android-папку. Никаких
   автоматических решений, слияния строк или перезаписи Markdown.
3. Доставить ту же ветвь ещё раз, затем старый подписанный её префикс —
   последний должен быть заблокирован high-water даже после удаления inbox.
   Настоящий новый fork из той же точки остаётся отдельным для просмотра.
4. Перенести защищённую историю high-water через отдельно включаемый импорт
   DPKSB по `docs/STAGE21_HIGHWATER_RECOVERY.md`; проверить объединение
   отметок без замены и отказ старому префиксу на новом устройстве.

## Каждая чужая операция — два явных шага

Перед подтверждением сверить локальную и чужую вершины, доверенный ключ,
полный предпросмотр и **отдельное повторное подтверждение**. После изменения
локального журнала/оригинала или отзыва доверия старый диалог обязан отказать.

| Операции | Проверить | Ожидаемый результат |
| --- | --- | --- |
| `accept` | Локальный Markdown, SHA, фрагмент, роль, прочтение | Новое локальное событие; спор — оставить локальное/пометить конфликт |
| `batch_accept` | **Все** 2–8 файлов, SHA, фрагменты, canonical claims | Одно атомарное локальное событие **или ничего** |
| `retract` | Активная локальная цель и последствия | Локальная проверенная отмена |
| `revise`, `split`, `merge` | Старые активные локальные узлы, новые ID и роли | Новое причинное событие; чужое provenance не становится доказательством |
| `schema`, `alias`, `label` | Полный ограниченный payload, отсутствие скрытого переопределения | Явно одобренная локальная метаоперация |
| `bind`, `resolve` | То же индексированное локальное предложение и живой слот/вариант | Новый локальный выбор, исходник неизменен |
| `defer`, `reject`, `peer_*` и непереносимый смысл | Не превращать чужой аудит в факт | Только локальный `hold/reject` receipt |

Для `batch_accept` специально изменить **одну** исходную заметку между
предпросмотром и подтверждением: нельзя записать даже остальные утверждения.
Для остальных операций изменить локальный журнал перед вторым подтверждением.

## Приёмочный протокол

- Проверить TalkBack, крупный шрифт, поворот, клавиатуру, закрытие диалога,
  возвращение из фона и восстановление после сбоя питания. Синтетический
  `PASS` не удостоверяет реальный UI, Keystore, файловый провайдер или ОС.
- QA-отчёт и логи не должны содержать приватных заметок, паролей, токенов,
  полных путей к личным файлам; можно скопировать только обезличенные статусы.
- Записать в корневой `TODO.md` по каждому QA-21-* версию тестовой APK (после
  отдельного разрешения), Android API/модель, дату, PASS/FAIL и безопасное
  описание отклонений. До завершения физических проверок **Stage 21 = NOT PASS**,
  а PR #74 остаётся черновым.

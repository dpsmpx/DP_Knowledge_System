# MODEL-M3 — подготовка E5-текста и контракт тензоров (без inference)

Этот этап добавляет Java-компоненты локального Android-эмбеддера:
явную маркировку запроса/фрагмента, проверку результата токенизатора,
маскированное усреднение скрытых состояний и экспериментальный **нативный
SentencePiece-адаптер** для вручную установленного `.model`.
Чтение реальных весов, их ONNX `Run` и построение индекса **не включены**.
Существующие веса по-прежнему помечаются неготовыми к исполнению.

## Почему нельзя подменить токенизатор

Курируемая [intfloat/multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small)
заявляет `XLMRobertaTokenizer`, `model_max_length=512` в
[`tokenizer_config.json`](https://huggingface.co/intfloat/multilingual-e5-small/blob/main/tokenizer_config.json).
Это SentencePiece/XLM-R, не BERT WordPiece. Сопоставление слов по `vocab.txt`
или самодельная разбивка Unicode без подтверждённого токенизатора давали бы
неверные ID. Модельная карточка требует префиксы `query: ` / `passage: `,
masked mean pooling и L2-нормализацию. Веса и сопутствующие файлы должны
быть зафиксированы и проверены перед исполнением.

## Уже проверяемый контракт

1. `KnowledgeE5Text.prepare(QUERY/PASSAGE, text)` добавляет **ровно один**
   явный префикс, сохраняет исходный Unicode/пробелы. Пустой ввод, повторный
   префикс, одиночные UTF-16 surrogate и текст длиннее 8192 UTF-16 единиц
   отклоняются; усечение исходного текста не выполняется молча.
2. `KnowledgeEmbeddingTensorContract.fromTokenizer(...)` принимает только
   готовые ID от явно вызываемого tokenizer adapter: один batch,
   3–512 токенов, BOS/содержимое/EOS, ровно бинарную `attention_mask`,
   только правую padding-зону с правильным pad ID. Не угадывает special
   ID по `config.json`, не приводит отрицательные ID и не делает
   токенизацию из строки. Флаг `tokenizerTruncated` сохраняется для
   явной диагностики потери хвоста. На выходе копии `int64[1][sequence]`
   для `input_ids` и `attention_mask`.
3. `poolAndNormalize(...)` требует **один** `float32[1][sequence][dim]`
   `last_hidden_state`, ожидаемую размерность 8–4096 (для E5 Small — 384),
   проверяет все размеры и значения, считает арифметическое среднее
   **только по активным токенам**, затем вызывает общий строгий
   `KnowledgeEmbeddingVectors.normalize`. Не принимает уже агрегированный
   `[1][dim]`, NaN/Inf или нулевой вектор.
4. Методы работают только с переданными в память синтетическими
   строками/массивами: без сети, файлов модели, заметок, Android UI или
   фоновых задач. Тесты покрывают Unicode, padding, спецтокены,
   граничные длины, копирование входа, усечение, mean pooling и
   отказ на некорректном ONNX-выводе.
5. Вход `token_type_ids` (если он объявлен в ONNX) строится из нулей
   для одной последовательности, копируется как `int64[1][sequence]`.
   Отдельный `KnowledgeE5OnnxSignature` требует точные имена
   `input_ids` / `attention_mask` / необязательный `token_type_ids`, тип
   `INT64`, rank 2, совместимые размеры batch/sequence; выход
   `last_hidden_state` обязан иметь `FLOAT32[1,sequence,dim]`.
   Допускается дополнительный `pooler_output`, но он не применяется
   для эмбеддинга. Неизвестные входы/выходы, типы, batch, длина и
   размерность отклоняются **до** исполнения модели.
6. Существующий *ручной* «Тест ONNX CPU» после Identity дополнительно
   исполняет **сгенерированный в памяти** мини-граф Gather с тремя
   числовыми `int64` входами и `float32[1,4,8]` выходом. Таблица всего
   из четырёх синтетических строк делает значение padding намеренно
   огромным; проверка сверяет результат masked-mean/L2 в изолированном
   CPU-процессе. Показанное пользователю время `inferenceMicros` всё ещё
   относится **только к прежнему Identity** и не измеряет производительность
   эмбеддингов, моделей или токенизатора. Нет нового фонового теста.
7. При ручном **аудите** установленных комплектов роли Embedding, если
   TOKENIZER представлен файлом `.model`, выполняется отдельный
   **потоковый read-only** осмотр его SentencePiece `ModelProto`: число
   частей словаря (до 500 000), тип BPE/Unigram, настройки normalizer,
   размер таблицы Unicode и **сырые** ID специальных частей.
   Программа не загружает словарь целиком в Java heap и не выполняет
   нормализацию текста. SHA-256 проверяется отдельно перед разбором.
   Некорректный `.model` оставляет факт совпадения SHA, но показывает
   предупреждение и блокирует ручную подготовку ONNX-пакета. Отсутствие
   `.model` не считается подтверждением поддержки токенизатора.
8. `KnowledgeE5SentencePiece.encode(...)` — отдельный **синхронный,
   неавтоматический** Android-адаптер для E5. Он проверяет метаданные BPE
   (`<unk>`=0, `<s>`=1, `</s>`=2, без PAD), подготавливает текст через
   `KnowledgeE5Text.prepare`, передаёт `путь + размер + ожидаемый SHA-256`
   в `ksys_e5_tokenizer.py`. Python читает **строго ограниченное** число
   байт локального файла без следования по симлинкам, считает SHA того же
   массива байт и только затем передаёт его нативному SentencePiece
   (`LoadFromSerializedProto`). Нормализация и BPE выполняются официальной
   библиотекой, а raw piece ID отображаются в словарь XLM-R так же, как у
   slow `XLMRobertaTokenizer` версии Transformers 4.57.1:
   неизвестный ID `0 → 3`, остальные `+1`, рамка `BOS=0` / `EOS=2`.
   Встроенные специальные токены внутри пользовательского текста
   отклоняются, незаметного усечения более 512 токенов нет. Результат
   проходит `KnowledgeEmbeddingTensorContract` с маской из единиц.
   Выполнять только на фоне, после явного выбора/проверки локального файла;
   адаптер **не подключён к автоматическому индексированию или ONNX Run**.
9. Только flavor `flavorAtest` получает нативный `sentencepiece==0.2.1`
   для Python 3.10; прочие flavors остаются на Python 3.11 без
   SentencePiece. Это связано с доступными официальными Android wheels
   Chaquopy. В CI проверяется импорт и кодирование **синтетического**
   SentencePiece BPE, отдельные host-тесты проверяют отказ при несовпадении
   SHA, нормализации спецтокенов и превышении лимитов. Это не заменяет
   сравнения с реальным E5 на целевой модели.

## Эталонные token ID без модели весов

`scripts/e5_sentencepiece_reference.py` — отдельная **необязательная**
host-side утилита. Она принимает только уже скачанный самим пользователем
`sentencepiece.bpe.model`, сверяет **ожидаемый SHA-256**, создаёт
`XLMRobertaTokenizer` с локальным файлом (пакеты `transformers` и
`sentencepiece` должны быть установлены заранее) и выводит JSON с ID
четырёх **жёстко заданных** тестов: английский, русский, китайский, эмодзи.
Скрипт не обращается к HF, не загружает веса, не читает заметки и
не сохраняет результат автоматически:

```bash
python scripts/e5_sentencepiece_reference.py \
  --sentencepiece /path/to/sentencepiece.bpe.model \
  --expected-sha256 YOUR_64_HEX_SHA256
```

Полученный JSON — основа будущей сверки Android tokenizer adapter, **не**
доказательство работы inference. Для настоящей эталонной проверки нужно
зафиксировать ревизию, фактический SHA и версии библиотек. В CI
проверяются только синтетические заглушки: внешняя модель не скачивается.

## Незакрытые этапы MODEL-M3

- Согласовать ревизию E5, файлы `sentencepiece.bpe.model`/`tokenizer.json`,
  настройки normalizer, special ID и соответствие SHA установленных
  sidecars; сравнить Android ID с эталонными для RU/EN/CJK и эмодзи на
  устройстве. Нативный adapter существует, но **реальный золотой E5
  тест и его автоматическое использование ещё не выполнены**.
  Популярный сторонний Java-порт `SentencePiece4J` не подключён:
  в проверенной версии присутствует принудительное приведение к нижнему
  регистру в одном кодовом пути, а модельно-точная нормализация E5 не
  подтверждена; токенизатор нельзя считать взаимозаменяемым без golden QA.
- На реальном ONNX артефакте проверить имена/типы/формы через ORT metadata,
  зафиксировать совместимую ревизию и связывать входы **по имени**.
  Синтетический Gather подтверждает только механизм, а не конкретный E5.
- Подключить изолированный native ORT backend только к одобренному
  пакету, провести золотые тесты с Python reference/Android и сценарии
  отмены, OOM/thermal, lifecycle, 20k-note migration и FTS fallback.
- Сравнить embeddings и качество извлечения на обезличенном фиксированном
  наборе; сохранить пользовательское ручное управление загрузкой и
  разрешением на индексирование. До этого `runnable()` остаётся `false`.

**Приёмка:** Android/JVM unit tests и Python regression CI — отдельно от
настоящих модельных и физических device QA.

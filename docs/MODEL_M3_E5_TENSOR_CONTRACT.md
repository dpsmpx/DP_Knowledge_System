# MODEL-M3 — подготовка E5-текста и контракт тензоров (без inference)

Этот этап добавляет Java-компоненты локального Android-эмбеддера:
явную маркировку запроса/фрагмента, проверку результата токенизатора,
маскированное усреднение скрытых состояний и экспериментальный **нативный
SentencePiece-адаптер** для вручную установленного `.model`.
Чтение реальных весов, их ONNX `Run` и построение индекса **не включены**.
Существующие веса по-прежнему помечаются неготовыми к исполнению.

## Почему нельзя подменить токенизатор

Курируемая [intfloat/multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small)
заявляет `XLMRobertaTokenizer`, `model_max_length=512` в
[`tokenizer_config.json`](https://huggingface.co/intfloat/multilingual-e5-small/blob/main/tokenizer_config.json).
Это SentencePiece/XLM-R, не BERT WordPiece. Сопоставление слов по `vocab.txt`
или самодельная разбивка Unicode без подтверждённого токенизатора давали бы
неверные ID. Модельная карточка требует префиксы `query: ` / `passage: `,
masked mean pooling и L2-нормализацию. Веса и сопутствующие файлы должны
быть зафиксированы и проверены перед исполнением.

## Уже проверяемый контракт

1. `KnowledgeE5Text.prepare(QUERY/PASSAGE, text)` добавляет **ровно один**
   явный префикс, сохраняет исходный Unicode/пробелы. Пустой ввод, повторный
   префикс, одиночные UTF-16 surrogate и текст длиннее 8192 UTF-16 единиц
   отклоняются; усечение исходного текста не выполняется молча.
2. `KnowledgeEmbeddingTensorContract.fromTokenizer(...)` принимает только
   готовые ID от явно вызываемого tokenizer adapter: один batch,
   3–512 токенов, BOS/содержимое/EOS, ровно бинарную `attention_mask`,
   только правую padding-зону с правильным pad ID. Не угадывает special
   ID по `config.json`, не приводит отрицательные ID и не делает
   токенизацию из строки. Флаг `tokenizerTruncated` сохраняется для
   явной диагностики потери хвоста. На выходе копии `int64[1][sequence]`
   для `input_ids` и `attention_mask`.
3. `poolAndNormalize(...)` требует **один** `float32[1][sequence][dim]`
   `last_hidden_state`, ожидаемую размерность 8–4096 (для E5 Small — 384),
   проверяет все размеры и значения, считает арифметическое среднее
   **только по активным токенам**, затем вызывает общий строгий
   `KnowledgeEmbeddingVectors.normalize`. Не принимает уже агрегированный
   `[1][dim]`, NaN/Inf или нулевой вектор.
4. Методы работают только с переданными в память синтетическими
   строками/массивами: без сети, файлов модели, заметок, Android UI или
   фоновых задач. Тесты покрывают Unicode, padding, спецтокены,
   граничные длины, копирование входа, усечение, mean pooling и
   отказ на некорректном ONNX-выводе.
5. Вход `token_type_ids` (если он объявлен в ONNX) строится из нулей
   для одной последовательности, копируется как `int64[1][sequence]`.
   Отдельный `KnowledgeE5OnnxSignature` требует точные имена
   `input_ids` / `attention_mask` / необязательный `token_type_ids`, тип
   `INT64`, rank 2, совместимые размеры batch/sequence; выход
   `last_hidden_state` обязан иметь `FLOAT32[1,sequence,dim]`.
   Допускается дополнительный `pooler_output`, но он не применяется
   для эмбеддинга. Неизвестные входы/выходы, типы, batch, длина и
   размерность отклоняются **до** исполнения модели.
6. Существующий *ручной* «Тест ONNX CPU» после Identity дополнительно
   исполняет **сгенерированный в памяти** мини-граф Gather с тремя
   числовыми `int64` входами и `float32[1,4,8]` выходом. Таблица всего
   из четырёх синтетических строк делает значение padding намеренно
   огромным; проверка сверяет результат masked-mean/L2 в изолированном
   CPU-процессе. Показанное пользователю время `inferenceMicros` всё ещё
   относится **только к прежнему Identity** и не измеряет производительность
   эмбеддингов, моделей или токенизатора. Нет нового фонового теста.
7. При ручном **аудите** установленных комплектов роли Embedding, если
   TOKENIZER представлен файлом `.model`, выполняется отдельный
   **потоковый read-only** осмотр его SentencePiece `ModelProto`: число
   частей словаря (до 500 000), тип BPE/Unigram, настройки normalizer,
   размер таблицы Unicode и **сырые** ID специальных частей.
   Программа не загружает словарь целиком в Java heap и не выполняет
   нормализацию текста. SHA-256 проверяется отдельно перед разбором.
   Некорректный `.model` оставляет факт совпадения SHA, но показывает
   предупреждение и блокирует ручную подготовку ONNX-пакета. Отсутствие
   `.model` не считается подтверждением поддержки токенизатора.
8. `KnowledgeE5SentencePiece.encode(...)` — отдельный **синхронный,
   неавтоматический** Android-адаптер для E5. Он проверяет метаданные BPE
   (`<unk>`=0, `<s>`=1, `</s>`=2, без PAD), подготавливает текст через
   `KnowledgeE5Text.prepare`, передаёт `путь + размер + ожидаемый SHA-256`
   в `ksys_e5_tokenizer.py`. Python читает **строго ограниченное** число
   байт локального файла без следования по симлинкам, считает SHA того же
   массива байт и только затем передаёт его нативному SentencePiece
   (`LoadFromSerializedProto`). Нормализация и BPE выполняются официальной
   библиотекой, а raw piece ID отображаются в словарь XLM-R так же, как у
   slow `XLMRobertaTokenizer` версии Transformers 4.57.1:
   неизвестный ID `0 → 3`, остальные `+1`, рамка `BOS=0` / `EOS=2`.
   Встроенные специальные токены внутри пользовательского текста
   отклоняются, незаметного усечения более 512 токенов нет. Результат
   проходит `KnowledgeEmbeddingTensorContract` с маской из единиц.
   Выполнять только на фоне, после явного выбора/проверки локального файла;
   адаптер **не подключён к автоматическому индексированию или ONNX Run**.
9. Только flavor `flavorAtest` получает нативный `sentencepiece==0.2.1`
   для Python 3.10; прочие flavors остаются на Python 3.11 без
   SentencePiece. Это связано с доступными официальными Android wheels
   Chaquopy. В CI проверяется импорт и кодирование **синтетического**
   SentencePiece BPE, отдельные host-тесты проверяют отказ при несовпадении
   SHA, нормализации спецтокенов и превышении лимитов. Это не заменяет
   сравнения с реальным E5 на целевой модели.
10. В управлении вручную установленным комплектом ONNX Embedding появился
    пункт **«Проверить токенизатор E5»**. Он требует заявленный источник
    `intfloat/multilingual-e5-small` (заявление пользователя, не
    криптографическое доказательство происхождения), ровно **один**
    SentencePiece `.model` в приватном пакете и его размер/SHA из
    манифеста. Четыре фиксированные строки пропускаются через нативный
    SentencePiece на фоне и строго проверенный тензорный контракт;
    выводятся длины последовательностей, SHA файла и **канонический SHA-256
    token ID**. Это отдельное, добровольное действие — без весов, заметок,
    сети, ONNX-inference и фонового расписания. При отмене дальнейшие
    шаги не выполняются, а результат не показывается. Кнопка копирования
    копирует только хеш синтетических token ID. Отпечаток **не доказывает
    паритет** до сравнения с независимым эталоном **того же файла**.

## Эталонные token ID без модели весов

`scripts/e5_sentencepiece_reference.py` — отдельная **необязательная**
host-side утилита. Она принимает только уже скачанный самим пользователем
`sentencepiece.bpe.model`, сверяет **ожидаемый SHA-256**, создаёт
**slow** `XLMRobertaTokenizer` из **Transformers 4.57.1** с локальным
файлом (пакеты `transformers==4.57.1` и `sentencepiece` должны быть
установлены заранее) и выводит JSON с ID
четырёх **жёстко заданных** тестов: английский, русский, китайский, эмодзи.
Скрипт не обращается к HF, не загружает веса, не читает заметки и
не сохраняет результат автоматически:

```bash
python scripts/e5_sentencepiece_reference.py \
  --sentencepiece /path/to/sentencepiece.bpe.model \
  --expected-sha256 YOUR_64_HEX_SHA256 \
  --android-fingerprint FINGERPRINT_COPIED_FROM_DPKS
```

Полученный JSON дополнительно содержит `golden_fingerprint_sha256`:
канонический SHA-256 по строкам `dpks-e5-golden-v1`, `model_sha256` и
алфавитно отсортированным строкам вида `имя=ID,ID,...`, разделённым `\n`
и с завершающим `\n`. Именно этот хеш показывается в Android при ручном
тесте. Необязательный аргумент `--android-fingerprint` выводит
`android_fingerprint_matches: true/false` и возвращает код `2` при
несовпадении; без него скрипт просто выводит эталон. Если хеши и SHA
`.model` совпадут — получено сильное доказательство
паритета **на четырёх фиксированных строках**, но не на всех возможных
строках, не готовности ONNX и не качества embeddings. В CI сверяется
независимый контрольный вектор хеширования для Java и Python без внешней
модели; реальный E5 `.model` по-прежнему никогда не скачивается в CI.

## Отдельный офлайн-эталон реальных ONNX-эмбеддингов на ПК

`scripts/e5_onnx_reference.py` — **добровольный host-side инструмент**,
который можно запустить на самостоятельно подготовленном E5-комплекте.
Он не вызывается Android-приложением, CI или фоновым расписанием.
Нужны заранее установленные `transformers==4.57.1`, `sentencepiece`,
`numpy`, `onnx`, `onnxruntime`; скрипт ничего не устанавливает и не
скачивает. Пример *после независимой проверки происхождения файла*:

```bash
python scripts/e5_onnx_reference.py \
  --manifest /path/to/verified-package/dpks-model-package.json \
  --expected-manifest-sha256 TRUSTED_64_HEX_SHA256
```

Для исполнения требуется **точный SHA-256 самого манифеста, заранее
зафиксированный независимо**. Скрипт строго читает `schema_version=1`,
`role=EMBEDDING`, `format=ONNX_UNVERIFIED` и
`source_id=intfloat/multilingual-e5-small`; проверяет все заявленные
файлы потоковым SHA-256, байтовые размеры, простые безопасные имена,
отсутствие символьных ссылок, канонический `config.json` и необязательный
`tokenizer_config.json`. Любое несовпадение блокирует загрузку native ML.
Это **не** доказывает истинность заявленного `source_id` или лицензии:
сами хеши нужно привязать к доверенной ревизии вне этого инструмента.

После preflight slow XLM-R токенизатор кодирует **ровно четыре встроенные
RU/EN/CJK/эмодзи строки** и формирует тот же золотой SHA token ID.
Скрипт сверяет имена, типы и оси ONNX Runtime, поддерживает 2/3 входа,
необязательный `pooler_output` и явный правый padding до фиксированной
длины графа. Только затем **по явной CLI-команде** выполняется один
`CPUExecutionProvider` `Run` на каждую строку; запрашивается только
`last_hidden_state`, после чего независимая скалярная реализация считает
masked mean/L2 с float32-округлением в соответствии с Java-контрактом.
JSON в stdout содержит контрольные SHA, token ID и все 384 компонента
четырёх нормализованных векторов. Заметки, пользовательские тексты и
файлы vault не открываются.

Для снижения рисков native-парсинга предварительно разбирается protobuf
через `onnx` и рекурсивно отклоняется **любой** TensorProto с
`external_data`, включая вложенные графы. Затем ORT получает **байты**
модели, а не путь к файлу. Эта версия не исполняет v2-комплекты с
внешними тензорами и ограничивает *именно host QA* файлом ONNX не более
1 ГиБ; общий Android-манифест и разрешение пользователю устанавливать
другие модели этим не изменяются. На ПК потребуется запас RAM сверх
размера файла, так как граф разбирается и загружается в память. Отсутствует
защита от целенаправленной конкурентной подмены файлов во время запуска;
тест предназначен для локального доверенного каталога.

Аргумент `--compare /path/to/android-reference.json` опционально
сопоставляет две JSON-выборки по SHA комплекта, golden fingerprint,
точным token ID/маскам и 384 float-компонентам с допуском `1e-5`.
Возвращается код `2`, если численная ошибка превышает допуск. **Android
пока не экспортирует реальные векторы в этом формате**: сравнение
подготовлено для следующего этапа, а не считается пройденным тестом.
CI использует исключительно маленькие фиктивные файлы и имитации
ONNX-метаданных; реальных весов, интернет-запросов и inference нет.

## Строгий профиль E5 Small перед ручной проверкой

`KnowledgeE5ConfigProfile` принимает только локальный `config.json` из
манифеста Embedding-пакета, который заявляет
`intfloat/multilingual-e5-small`. Код повторно читает не более 64 КиБ
**самого сохранённого файла**, сверяет точную длину и SHA-256 и разбирает
строгий UTF-8 JSON. Для курируемой ревизии проверяются `model_type=bert`,
`tokenizer_class=XLMRobertaTokenizer`, `hidden_size=384`,
`max_position_embeddings=512`, `vocab_size=250037`, 12 слоёв и голов,
`intermediate_size=1536`, `type_vocab_size=2`, `hidden_act=gelu` и
абсолютные позиционные эмбеддинги. Неизвестные дополнительные поля
оригинальной конфигурации разрешены, но требуемые поля обязаны совпасть.

Важная особенность [официального `config.json`](https://huggingface.co/intfloat/multilingual-e5-small/blob/main/config.json):
`pad_token_id=0` там относится к **BERT-конфигурации модели**;
`<pad>=1` относится к **XLM-R токенизатору**. Сравнивать эти ID друг
с другом нельзя; токенизатор продолжает выводить собственные
специальные ID и маски без догадок по модельному config.

Если установлен `tokenizer_config.json` (роль `TOKENIZER` или
`MODEL_CONFIG`), он также ограничивается 64 КиБ, повторно хешируется
и сверяется по имени класса, BOS/CLS/EOS/SEP/PAD/UNK,
`model_max_length=512`, пустому `sp_model_kwargs`. При несовпадении
ручная проверка отпечатка не запускается. Отсутствие *опционального*
файла не блокирует работу; отсутствие `config.json` блокирует.
`KnowledgeE5OnnxSignature.requireE5Small` дополнительно связывает
проверенный профиль с именами/типами и `384` каналами графа.

Это **предварительная проверка метаданных**, не доказательство
происхождения ревизии, эквивалентности реальной SentencePiece-модели,
успеха ONNX `Run` или совместимости весов. Ручной golden QA остаётся
локальным, а `runnable()` — `false`. JVM/Android CI использует только
синтетические данные и файлы, без скачивания моделей.

## Отдельная ручная проверка ONNX GraphProto без ORT-сессии

Пункт **«Проверить входы/выходы ONNX E5»** доступен для вручную
установленного ONNX Embedding-пакета, заявляющего
`intfloat/multilingual-e5-small`. Он **не использует лимит 16 МиБ**
старого теста ORT session, поскольку большие файлы E5 нельзя передавать
как один `byte[]` в изолированный сервис. После явного подтверждения
приложение в рабочем потоке:

1. Проверяет канонические `config.json` и необязательный
   `tokenizer_config.json` по манифесту и SHA-256.
2. Повторно хеширует все сохранённые **веса и sidecars**, запускает
   существующий read-only контейнерный аудит и проверяет объявления
   внешних файлов без открытия путей, взятых из ONNX.
3. Через `RandomAccessFile` читает только вложенные объявления
   `ModelProto.graph` → `GraphProto.input/output` → `ValueInfoProto.type`
   → `tensor_type.shape`. Данные тензоров и узлов пропускает
   ограниченным `seek`, не выделяя память под веса. Имена входов/выходов
   (`input_ids`, `attention_mask`, опциональный `token_type_ids`,
   `last_hidden_state`, опциональный `pooler_output`), ONNX типы
   (`INT64`/`FLOAT32`), batch/sequence и каналы `384` сравниваются
   с `KnowledgeE5OnnxSignature.requireE5Small`.
4. Показывает только число входов, выходов, динамических осей,
   проверенных байт и длительность. Пути, символические названия осей,
   внутренние имена узлов и пользовательские данные в отчёт не попадают.

Повреждённые protobuf-длины, дублированные имена/поля, чрезмерные
вложения, неверные типы и размерности отклоняются. Тесты используют
синтетические protobuf-файлы, в том числе с крупным полем initializer,
и проверяют отказ при подмене веса после установки пакета.

Это только **статическая проверка объявлений**. Совпадение формы не
доказывает, что граф имеет поддерживаемые операторы или что реальные
веса корректно выполняются ONNX Runtime. Никакая ORT-сессия не создаётся,
токенизация и индексация не запускаются, `runnable()` остаётся `false`.

## Независимая проверка ONNX Runtime на синтетических E5-формах

Для `flavorAtest` инструментальный Android-тест использует только
**сгенерированный** Gather-граф с таблицей из четырёх строк и 384
каналами (также отдельный отрицательный пример с 768 каналами).
Тот же маленький файл анализируется read-only protobuf-парсером,
а затем ONNX Runtime загружает его **только для получения метаданных**.
Тест сравнивает поимённо все типы и оси входов/выходов двух независимых
декодеров, проверяет положительный профиль 384 и отказ профиля 768.
`session.run()` **не вызывается**. Базовый синтетический Gather smoke
с восемью каналами и masked mean сохраняется без изменений.

Этот тест подтверждает только согласованность двух читателей
**на контролируемых графах**, не паритет на настоящем E5, не доступность
большой модели в ORT и не точность эмбеддингов. Реальные файлы E5
не скачиваются, не кладутся в APK и не входят в CI; ручной статический
preflight остаётся без native ORT-сессии. Пользовательский vault
и сеть не затрагиваются.

## Синтетическая цепочка SentencePiece → ONNX → masked mean/L2

Отдельный Android instrumented-тест объединяет ранее изолированные
компоненты: генерирует небольшой BPE SentencePiece `.model`, сверяет
его размер/SHA-256 и нативно кодирует `query: hi` с XLM-R ID;
затем добавляет **две правые PAD-позиции** (`<pad>=1`, маска `0`)
после EOS и строит `int64[1, sequence]` для трёх именованных входов.
Выходной граф `KnowledgeE5TokenEmbeddingSmoke.graph(sequence)` генерируется
только для теста: 32 строки арифметических значений по 384 канала,
операторы `Sub/Add/Gather`, без обученных весов и без файлов пользователя.

Граф проходит тот же статический E5 metadata gate и сверку форм с
native ORT, после чего **только синтетический тест** вызывает
`session.run()` с созданными ID и маской. Строка lookup для PAD содержит
значение `10000` и гарантированно присутствует в выходе ONNX,
но должна полностью игнорироваться при pooling. Java-пуллер делает
masked mean/L2, а результат по всем 384 компонентам сравнивается
с независимой скалярной реализацией той же арифметической таблицы.
Неправомерно активная PAD-позиция отклоняется ещё на тензорном контракте.

Таким образом проверяется перенос ID через native SentencePiece и
ONNX Runtime до нормализованного синтетического вектора, но **не**
численная точность настоящей модели E5, не качество поиска, не
производительность и не пригодность установленных весов.
Этот тест не запускается автоматически в пользовательском приложении:
только в CI на эмуляторах с тестовым flavor. Vault, сеть и реальные
веса не используются; `runnable()` остаётся `false`.

## Изолированная от продукта подготовка именованного ONNX Run

`KnowledgeE5OrtTensorRunner` существует **только** в тестовом
`flavorAtest`. Он не выбирает модель или путь к файлу и не включён
в индексирование. Вызывающий код передаёт уже открытую сессию,
канонический профиль E5 и проверенный набор токенов. Перед входом в
нативный `run()` адаптер заново сравнивает I/O-сигнатуры с профилем,
проверяет фиксированные длины осей относительно фактического batch,
отклоняет усечённые токены, некорректные XLM-R BOS/EOS/PAD и ID
вне словаря `250037`.

В ONNX передаются только объявленные графом входы с именами
`input_ids`, `attention_mask` и, если требуется, `token_type_ids`.
Результат запрашивается **по имени** `last_hidden_state`: необязательный
`pooler_output` не извлекается и никогда не используется для эмбеддинга.
Все входные ONNX-тензоры и результат закрываются по завершении; форма,
конечность и нормализация вектора повторно проверяются. Отмена
проверяется до и после вызова.

Тесты охватывают **две и три** обязательные для разных экспортов формы
входов, наличие двух выходов с намеренно NaN-значениями в неиспользуемом
`pooler_output`, несоответствие фиксированной длины токенов, неверные
специальные ID и запрет усечённого токенизатора. Все графы сгенерированы,
не содержат реальных весов. Это лишь подготовка безопасного интерфейса,
а не разрешение использовать установленную модель или заметки.

### Прерывание native Run и предварительная оценка памяти

Тестовый E5-runner теперь создаёт отдельный `OrtSession.RunOptions` для
**каждого** вызова и передаёт его в `session.run(..., requestedOutputs,
runOptions)`. Одноразовый `StopSignal` синхронизирует вызовы из другого
потока: `cancel()` устанавливает флаг отмены и, если Run активен,
запрашивает **best-effort** `RunOptions.setTerminate(true)` у ONNX Runtime.
До первого создания тензоров, непосредственно перед `Run`, после него и
после pooling флаг проверяется повторно. При ошибке native ORT во время
отмены наружу передаётся только контролируемое исключение; дескрипторы
`RunOptions`, результата и входных тензоров закрываются. После завершения
активный `RunOptions` отсоединяется, отменённый сигнал повторно не
используется. Эмуляторный тест проверяет межпоточную отмену активного
`RunOptions` и запрет запуска заранее отменённого batch.

`setTerminate` не является гарантией остановки зависшего native-кода:
**обязательным последним рубежом** остаётся уже существующий watchdog
изолированного процесса с аварийным завершением *только worker*, а не
основного приложения. Текущий E5-runner по-прежнему вызывается только
тестами, а **реальная** связка с изолированным worker ещё не создана.

Новый `KnowledgeE5ResourceEstimate` считает точные размеры трёх или двух
входных `int64`-тензоров и выходного `float32[1,seq,384]`. Для будущего
ручного UI он отдельно формирует грубый ориентир рабочей памяти
`2 × байты ONNX + байты external_data + 128 МиБ + тензоры` и предупреждает,
когда он превышает доступную RAM за вычетом 256 МиБ. **Это не замер пика
RAM и не резервирование памяти**; коэффициент может не соответствовать
конкретному графу, движку или устройству. Если свежий системный снимок
показывает `lowMemory` либо менее 512 МиБ свободной RAM, план отмечается
как недопустимый. Большая пользовательская модель сама по себе не
блокируется произвольным лимитом размера — выдаётся предупреждение.
JVM-тесты покрывают границы, переполнение арифметики, low-memory и
разницу 2/3 входов; никакие веса ради оценки не открываются.

Оценка пока **не подключена** к реальному E5 executor. Перед включением
потребуются свежий системный снимок *из worker*, повторное хеширование
всего установленного комплекта, ограничение времени/памяти во время
нативного Run и отдельные тесты повреждения/отмены на настоящих весах.

## Незакрытые этапы MODEL-M3

- Согласовать ревизию E5, файлы `sentencepiece.bpe.model`/`tokenizer.json`,
  настройки normalizer, special ID и соответствие SHA установленных
  sidecars; сравнить Android ID с эталонными для RU/EN/CJK и эмодзи на
  устройстве. Ручной путь сравнения отпечатков добавлен, но **реальный
  E5 файл не входил в CI, поэтому фактический золотой паритет ещё
  не подтверждён**.
  Популярный сторонний Java-порт `SentencePiece4J` не подключён:
  в проверенной версии присутствует принудительное приведение к нижнему
  регистру в одном кодовом пути, а модельно-точная нормализация E5 не
  подтверждена; токенизатор нельзя считать взаимозаменяемым без golden QA.
- На реальном ONNX артефакте дополнительно проверить имена/типы/формы
  через **ORT metadata** в изолированном процессе, зафиксировать
  совместимую ревизию и связывать входы **по имени**. Ручной protobuf
  preflight теперь проверяет объявления без запуска движка; он не
  заменяет ORT metadata и не доказывает совместимость конкретного E5.
- Подключить изолированный native ORT backend только к одобренному
  пакету, провести золотые тесты с Python reference/Android и сценарии
  отмены, OOM/thermal, lifecycle, 20k-note migration и FTS fallback.
- Сравнить embeddings и качество извлечения на обезличенном фиксированном
  наборе; сохранить пользовательское ручное управление загрузкой и
  разрешением на индексирование. До этого `runnable()` остаётся `false`.

**Приёмка:** Android/JVM unit tests и Python regression CI — отдельно от
настоящих модельных и физических device QA.

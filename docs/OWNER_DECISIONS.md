# DP Knowledge System — решения владельца

**Обновлено 2026-11-19.** Решения ниже получены от владельца в обсуждении
плана этапов 15–23. Здесь нет личных заметок, реальных путей, ключей или
других пользовательских данных.

| ID | Принятое направление | Последствия для разработки |
|---|---|---|
| **Q-01** | Первой разрабатывается Android-версия. Интерфейс платформы отделён от переносимого ядра. | Не блокировать Android v1 ожиданием desktop/web; сохранить явные границы модулей. |
| **Q-02** | Поддержка старых Android не требуется. | Текущий `minSdk` не обязателен как долгосрочная граница; изменение — отдельный проверенный PR с объяснением диапазона устройств. |
| **Q-03** | Основной масштаб для проектирования — **20 000** заметок. Точный допустимый срок первой индексации не установлен. | Профилировать 20k; 200k — дополнительное исследование, а не условие первой версии. Любую неполноту явно показывать. |
| **Q-04** | Безопасные действия допустимы автоматически; действия с риском изменения содержимого/структуры требуют одобрения. Оригиналы сохраняются в ZIP-бэкапе внутри приложения. | Разделить действия по уровням риска, предпросмотр, журнал и возможность восстановления; не приписывать модели авторитет. |
| **Q-05** | Требуются и встроенная синхронизация, и совместимость с внешними средствами, а также резервные копии доступными провайдерами, включая Google Drive. | Спроектировать конфликты и merge журнала решений отдельно; не включать автоматическую синхронизацию без шифрования и контроля. |
| **Q-06** | Поддерживать три режима моделей: on-device Android, локальный ПК (LAN/Tailscale) и облачный API. **Локальная модель предпочтительна, но не обязательна.** | Отделить AI-провайдеры от ядра, показывать согласие перед внешней передачей. При отсутствии модели приложение полноценно использует детерминированные функции. |
| **Q-07** | Защищённое хранение секретов обязательно. Полный экспорт/импорт настроек, заметок и прочих данных; Android-защита секретов и парольное шифрование архива. | Разделить данные и ключи Android Keystore, проектировать переносимость и восстановление на другом устройстве, никогда не экспортировать ключи открытым текстом. |
| **Q-08** | Нужны пакетное принятие и автоматические решения **при строгих критериях**. | Разделить формальные проверяемые безопасные действия и авторитетные решения; для автоматизации сначала определить запреты, условия и аудируемые правила, не активировать её по умолчанию без отдельного дизайна. |
| **Q-09** | Полная переработка UI: современные мобильные паттерны, динамические темы, производительный рендеринг, системная интеграция, видимый прогресс и предпросмотр изменений; минимализм по философии Obsidian без копирования интерфейса. | Отдельный этап UX и доступности; текущий форк Markor — переходная основа, не конечный дизайн. |
| **Q-10** | Для первой публикации **GitHub Releases и RuStore**. | Два воспроизводимых канала с раздельной проверкой артефактов и требований к подписи/разрешениям. |
| **Q-11** | Автоматическое резервное копирование раз в день по умолчанию, пользователь может изменить период. | Надёжная очередь, зашифрованные архивы, выбор места, удержание версий, восстановление без потерь, учёт OEM-ограничений. |
| **Q-12** | Предложенная очередность Stage 15 → 16–22 → release gate 23 принята; старые ручные проверки остаются долгами. | Сначала достоверность источников/целостность, затем знания, поиск, производительность, переносимость и UX. |

## Обязательные защитные ограничения до реализации автоматизации

- Оригинальные файлы не менять без явно понятного пользователю права на
  конкретный класс операции, dry-run и истории обратимых изменений.
- Извлечённые утверждения — кандидаты, а не факты. Запрос на **автопринятие**
  не является разрешением текущему прототипу менять авторитетный журнал:
  требуется отдельная спецификация строгих критериев, тестов и режима отзыва.
- Секреты не покидают защищённое хранилище в открытом виде; сторонним
  AI-сервисам текст передаётся только после просмотра точного outbound-контекста.
- Облачный backup/sync нельзя путать с доставкой исходных Markdown в
  публичный репозиторий; приватные пользовательские данные остаются приватными.

## Остающиеся технические вопросы

Не блокируют Stage 16: точный список моделей и аппаратные лимиты on-device
AI; формат и правила конфликтного слияния журнала; критерии автоматического
принятия; политика хранения/ротации резервных копий и ключей; решения по
минимальному Android API и подписи релизов для RuStore. Они остаются
предметом отдельного проектирования по этапам 17, 20–23.
